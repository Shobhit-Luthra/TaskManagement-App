# Engineering Rules

These rules apply to every project you work on.

The goal is to produce production-level software without unnecessary complexity, unnecessary refactoring, security negligence, or uncontrolled scope expansion.

## 1. Production-Level Code

Write code as if it will be deployed to production.

Prioritize:
- Correctness
- Security
- Reliability
- Maintainability
- Performance
- Scalability
- Testability
- Clear architecture

Do not write disposable or demo-quality code unless explicitly requested.

Do not use fake implementations, placeholder logic, random data, or mocked behavior in production paths unless explicitly requested. Clearly identify intentional mocks.

## 2. Do Not Overthink

Prefer the simplest production-appropriate solution.

Do not introduce unnecessary abstractions, design patterns, dependencies, microservices, complex state management, excessive configuration, premature optimization, caching, or infrastructure.

Use complexity only when requirements justify it.

## 3. Do Not Make Unnecessary Changes

When implementing a feature or fixing a bug, change only what is necessary.

Do not rewrite unrelated code, refactor unrelated files, rename things unnecessarily, change architecture without reason, replace working libraries without justification, or modify unrelated behavior.

Keep the diff focused. Mention unrelated technical debt separately instead of silently changing it.

## 4. Keep the File Structure Clean

Maintain a clean and logical project structure.

Before creating a new file:
1. Check whether an existing file already handles the responsibility.
2. Check whether the functionality belongs in an existing module.
3. Determine whether a new abstraction is justified.

Avoid duplicate utilities, components, services, random helper files, unused files, temporary/debug files, and unnecessary nested directories.

Remove files that are no longer needed.

## 5. Understand Before Modifying

Before modifying existing functionality:
1. Inspect the relevant code.
2. Understand the current implementation.
3. Identify dependencies and side effects.
4. Identify affected components.
5. Determine the smallest correct change.

Do not modify code based on assumptions when the repository can answer the question.

## 6. Security Scan Before Every Commit

Before every Git commit, perform a security review of the changes being committed.

Check for:
- Hardcoded secrets
- API keys
- Passwords
- Tokens
- Private credentials
- Sensitive data exposure
- Authentication bypass
- Authorization issues
- Missing input validation
- SQL injection
- XSS
- CSRF where applicable
- Command injection
- Path traversal
- SSRF where applicable
- Unsafe file uploads
- Insecure deserialization
- Dependency vulnerabilities
- Excessive permissions
- Information leakage
- Debug endpoints
- Unsafe logging

Inspect the Git diff before committing.

If a security issue is found, do not commit until it is resolved unless explicitly instructed otherwise.

Never commit secrets, even temporarily.

## 7. Never Make Yourself the Git Author

Never add Claude, Anthropic, an AI agent, or any AI identity as an author or co-author of Git commits.

Do not add:
- `Co-authored-by: Claude`
- `Co-authored-by: Anthropic`
- `Generated by Claude`
- `AI-generated`

unless explicitly requested.

Do not modify Git identity to impersonate the user.

Use the Git identity already configured by the repository/user.

## 8. Git Commit Rules

Before creating a commit:
1. Inspect `git status`.
2. Inspect the diff.
3. Check for unintended files.
4. Check for secrets.
5. Perform the security review.
6. Run relevant tests.
7. Verify the application/build where appropriate.
8. Only then create the commit.

Never blindly commit everything with `git add .` without first verifying the files.

Prefer targeted staging when appropriate.

Commit logically related changes together.

## 9. Security Is Not an Afterthought

For every feature involving user-controlled input ask:
- What can the user control?
- Where does the input go?
- Is it validated?
- Is it sanitized where appropriate?
- Is it authorized?
- Could it reach a database?
- Could it reach a shell/command?
- Could it reach an external URL?
- Could it be rendered as HTML?
- Could it affect another user's data?
- Could it expose sensitive information?

Never assume frontend validation is sufficient. Critical validation and authorization must exist server-side.

## 10. Input Validation

Treat all external input as untrusted, including HTTP requests, query parameters, URL parameters, forms, JSON, file uploads, cookies, headers, webhooks, third-party responses, and AI-generated output.

Validate:
- Type
- Format
- Length
- Range
- Allowed values
- Relationships
- Authorization

Reject invalid input safely.

## 11. Authentication vs Authorization

Authentication answers: Who is this user?

Authorization answers: What is this user allowed to do?

Never rely solely on frontend checks for authorization.

Sensitive operations must be authorized on the backend.

Users must not be able to access another user's resources simply by changing an ID. Always consider IDOR/BOLA-style vulnerabilities.

## 12. Production Error Handling

Every important operation must account for:
- Invalid input
- Missing data
- Unauthorized access
- Database failure
- Network failure
- Timeout
- Rate limiting
- Third-party API failure
- Duplicate requests
- Concurrent requests
- Partial failure
- Service unavailable
- Unexpected exceptions

Do not implement only the happy path.

Never expose internal stack traces, secrets, database details, or sensitive information to users.

## 13. Network Reliability

For external/network operations consider:
- Timeouts
- Retries
- Retry limits
- Exponential backoff where appropriate
- Idempotency
- Connection failures
- Partial responses
- Rate limits
- Service outages

Do not blindly retry operations that are not safe to repeat.

Be particularly careful with payments, reservations, orders, resource allocation, emails, notifications, and database mutations.

## 14. State Management

Before introducing or changing application state, ask:
- Where should this state live?
- Is it local UI state?
- Server state?
- URL state?
- Persistent state?
- Global application state?

Do not put everything into global state.

Avoid duplicated sources of truth.

Prefer the simplest state-management approach that satisfies the requirements.

## 15. Database Safety

Before changing database behavior consider:
- Data integrity
- Constraints
- Transactions
- Concurrency
- Race conditions
- Indexes
- Query performance
- Migration safety
- Existing production data

Never casually modify or delete production data.

Do not write destructive migrations without understanding their consequences.

For shared resources, explicitly consider concurrent requests.

## 16. Performance

Do not prematurely optimize.

Before finalizing a feature, ask:
- Could this create N+1 queries?
- Could this load too much data?
- Could this trigger unnecessary API requests?
- Could this cause excessive re-renders?
- Could this block the main thread?
- Could this create an expensive database query?
- Could this grow poorly with data size?
- Could this generate excessive AI/API costs?

Fix obvious bottlenecks without introducing unnecessary complexity.

## 17. Scaling Review

For significant architectural decisions, explicitly ask:

> Are there hidden scaling bottlenecks or state-management issues with the approach I am planning?

Consider:
- Number of users
- Concurrent users
- Database growth
- Request volume
- Memory usage
- Background jobs
- Queues
- External API limits
- AI model limits
- Storage growth
- Connection pools
- Rate limits

Do not prematurely design for millions of users if the project does not require it. However, do not introduce architecture that obviously prevents reasonable future growth.

## 18. Devil's Advocate Review

Before finalizing a significant feature or architecture, ask:

> Play devil’s advocate: where is this design or logic most likely to break under production loads?

Evaluate:
- Failure points
- Race conditions
- Data corruption
- Performance bottlenecks
- Security weaknesses
- Dependency failures
- Unexpected user behavior
- Operational complexity
- Scaling problems

Address serious weaknesses before considering the implementation complete.

## 19. Security Question

For every significant feature ask:

> What security vulnerabilities or missing input-validation risks am I overlooking in this feature?

Consider:
- Trust boundaries
- User input
- Authorization
- Data exposure
- Injection
- File handling
- Authentication
- Rate limiting
- Abuse scenarios
- Third-party integrations

## 20. Error-State Question

Before writing code for a significant feature ask:

> What potential error states, network timeouts, or edge cases do we need to handle before writing code?

Consider:
- Invalid input
- Missing input
- Unauthorized actions
- Duplicate actions
- Database unavailable
- API timeout
- Third-party failure
- AI failure
- Network interruption
- Race conditions
- Partial failure
- Loading
- Empty
- Error
- Success
- Disabled
- Offline/connection lost
- Retry

## 21. Explain Code Like a PR Review

When asked:

> Explain this code like you're walking me through a PR review

Explain it as a senior engineer reviewing the pull request.

Cover:
1. What changed
2. How it works
3. Why it was implemented this way
4. Bugs/security/performance/maintainability concerns
5. What should be changed
6. Verdict: Approve / Approve with minor changes / Request changes

Do not explain every line if it adds no value. Focus on decisions, behavior, risks, and maintainability.

## 22. Avoid Fake Confidence

Never claim something is secure, production-ready, definitely working, or fully tested unless you actually verified it.

Distinguish clearly between:
- Verified
- Tested
- Reasoned about
- Assumed
- Not yet tested

## 23. Testing Before Completion

Before considering a change complete:
1. Run relevant tests.
2. Run linting/type checks where applicable.
3. Build the application where applicable.
4. Test important user flows.
5. Review error states.
6. Review authorization.
7. Review security.
8. Inspect the final diff.

For bugs, add a regression test when practical.

## 24. Documentation

Update documentation when behavior or architecture changes.

Do not create documentation for the sake of creating documentation.

Documentation should help someone understand:
- What the system does
- How it works
- How to run it
- How to configure it
- Important architectural decisions
- Important limitations

Keep documentation synchronized with the code.

## 25. Dependency Discipline

Before adding a package:
1. Check whether the existing stack already solves the problem.
2. Check whether the framework provides the functionality.
3. Consider whether the dependency is maintained.
4. Consider security.
5. Consider bundle/runtime impact.
6. Consider long-term maintenance.

Do not add dependencies for trivial functionality.

## 26. Refactoring Rules

Refactor when it provides clear value.

Do not refactor unrelated code while implementing a feature.

A refactor should have a clear reason such as:
- Removing duplication
- Fixing architectural coupling
- Improving maintainability
- Fixing a known performance issue
- Improving testability
- Fixing a security problem

Avoid "while I'm here" refactoring.

## 27. AI/LLM Code

If the project uses AI, treat AI output as untrusted.

Validate AI-generated:
- Structured data
- Commands
- URLs
- Database operations
- User-facing content
- Decisions

Never allow an LLM to bypass normal authorization or business rules.

Consider:
- Prompt injection
- Data exfiltration
- Hallucination
- Tool misuse
- Excessive permissions
- Token costs
- Rate limits
- Model failure
- Timeout
- Fallback behavior

Use deterministic logic whenever it is more appropriate.

## 28. Secrets

Never expose secrets in:
- Source code
- Git commits
- Logs
- Error messages
- Client-side bundles
- Screenshots
- Documentation

If a secret is accidentally discovered:
1. Stop.
2. Do not commit it.
3. Alert me.
4. Recommend rotation/revocation.

## 29. Final Pre-Commit Checklist

Before EVERY commit:

- [ ] `git status` reviewed
- [ ] `git diff` reviewed
- [ ] Only intended files are staged
- [ ] No secrets or credentials
- [ ] Security vulnerabilities reviewed
- [ ] Input validation reviewed
- [ ] Authorization reviewed
- [ ] Error states reviewed
- [ ] Network failures/timeouts reviewed
- [ ] Relevant tests pass
- [ ] Build/typecheck/lint passes where applicable
- [ ] No unnecessary changes
- [ ] No debug code
- [ ] No temporary files
- [ ] No unnecessary dependencies
- [ ] Commit does not contain AI/Claude/Anthropic authorship

If a critical item fails, do not commit unless explicitly instructed otherwise.

## 30. Final Engineering Principle

Always optimize for:

**Correctness > Security > Reliability > Maintainability > Performance > Cleverness**

Remember:

> Build the simplest system that correctly solves the problem.

> Do not over-engineer.

> Do not under-engineer security.

> Do not make unrelated changes.

> Do not commit unverified work.

> Think like the software will actually have to survive production.
